# Glossary

Plain-language meanings of every term used in local-docs. If a term appears in
this project and isn't here, that's a bug — add it.

## local-docs terms

**Docs set** — One product's documentation at one version, stored in its own
folder: `libraries/<slug>/<version>/`. The unit everything else is built around:
agents pick a docs set from [INDEX.md](INDEX.md), then search inside it.

**Slug** — The short lower-case name used as a folder name, e.g. `gitea` or
`stripe-api`. Lets agents find a product without guessing capitalisation or
spacing. Each slug is one folder under `libraries/`.

**Ingest** — Find, download, clean and file a product's official docs as a new
docs set. Done by the `docs-library-ingest` skill
([skills/docs-library-ingest/SKILL.md](skills/docs-library-ingest/SKILL.md)).

**Refresh** — Re-ingest a docs set that already exists, replacing its contents
(for example after the docs were corrected upstream).

**Index** — [INDEX.md](INDEX.md): the catalogue of every docs set, one row
each. Generated by `tools/finalize.py`; agents read it first.

**Manifest** — `manifest.json` inside each docs set: a machine-readable record
of what the docs are, which version, where they came from (URLs, git commit),
what they cover and what's missing. It's how a reader can trust — or doubt —
what they find.

**Overview** — `OVERVIEW.md` inside each docs set: a page written for other
agents, explaining how the docs are laid out, which file answers which common
question, and what changed in this version.

**TOC (table of contents)** — `TOC.md` inside each docs set, listing every
document with its title. Generated; used when keyword searches miss.

**Companions** — Other packages bundled in one docs set with their own version
numbers, recorded in the manifest's `companions` field. Example: the Milvus 3.0
set also documents the Python SDK pymilvus 3.0.2 and Milvus Lite 3.2.2.

**Transclusion / includes** — When a docs site pulls the text of one file into
another while building the site (e.g. `{{fragments/x.md}}`, or a Next.js page
that only says `source: other/page`). Ingest copies the text in, so each stored
page is complete on its own.

**Local-only docs set** — A docs set kept on this machine and never committed,
because its licence doesn't allow republishing it in this public repository (e.g.
Tailscale's docs, © Tailscale Inc.). Its manifest says `"local_only": true`, its
folder is in `.gitignore`, and it is listed in `INDEX.local.md` (also git-ignored)
instead of `INDEX.md`. Search and `docs_list` include it on this machine only.

**Coverage / gaps** — Fields in the manifest. Coverage says what was ingested;
gaps says what a user might expect but isn't there (e.g. "blog not included").

**Version constraint** — The version rule in the request, e.g. "1.25 or later",
"^4", "latest". The ingest skill turns it into one exact release, the *resolved
version*.

**Resolved version** — The one exact release chosen to satisfy a version
constraint — normally the newest stable release that fits. It becomes the
docs set's folder name.

**Release line** — A family of releases a docs site documents as one version,
e.g. Gitea "28" covers 28.0.0 to 28.3.0. When a site publishes docs per release
line rather than per exact release, the docs set's folder is named after the
line (`libraries/gitea/28/`) and the exact newest release is recorded in the
manifest's optional `release` field (`"release": "28.3.0"`).

**Release variables (placeholders)** — Markers like `@version@` that some docs
sites write in their Markdown and replace with real values (a version number, a
Docker tag) when the site is built. Ingested docs have them filled in with the
values the site uses, so a search for `28.3.0` finds them; the manifest's
`notes` says when this was done.

**Source (of a docs set)** — One place a docs set's content came from, recorded
as an entry in the manifest's `sources` list with its type (`git`, `llms-txt`,
`package`, `crawl`, `openapi`, `graphql`, `release-notes`, `other`), URL, and
`dest` — the folder or file inside the docs set where it landed.

**Doc files / spec files** — Counts `finalize.py` puts in the manifest's `stats`.
Doc files are readable documentation (`.md`, `.rst`, `.txt`…); spec files are
machine-readable API contracts kept in `api/` (OpenAPI JSON/YAML, GraphQL,
protobuf).

**Docs-generator metadata** — Files a docs-site generator uses to build menus
and sidebars (`_category_.json`, `sidebars.js`, `_meta.json`), not
documentation. Removed during ingest.

**Archived repository** — A git repository its owners have frozen read-only,
usually because the project moved elsewhere. Docs from one are likely stale,
so the ingest skill checks for this before using a repo.

**Staging** — `.staging/`, a scratch folder where tools temporarily download
things before copying the useful part into a docs set. Git-ignored and emptied
automatically.

**Finalize** — Run `tools/finalize.py` on a docs set: validate its manifest and
overview, write its TOC and stats, rebuild the index. An ingest isn't done
until it prints `OK`.

## Claude Code terms

**Skill** — A folder with a `SKILL.md` file of instructions that Claude Code loads
when a request matches the skill's description. This project has two: `docs-library`
(look things up) and `docs-library-ingest` (add docs). They are not named
`local-docs`, which is the separate weekly-synced mirror skill. They live in `skills/` and
are linked into `~/.claude/skills` by `tools/install-skills.sh` so they work in
every project.

**Agent / subagent** — A Claude instance doing a task. A subagent is one started
by another agent to do part of the work; it sees only its instructions, which is
why the skills spell everything out.

**`CLAUDE.md`** — A file of standing instructions Claude Code reads automatically.
This project's [CLAUDE.md](CLAUDE.md) holds the rules for working here;
`~/.claude/CLAUDE.md` holds global instructions and points at local-docs.

## Documentation sources and formats

**Official source** — Documentation published by the people who make the
product: their docs site, their git repository, their package. Third-party
blogs and Q&A sites are never used.

**Release / tag / release branch** — A *release* is a numbered version a project
publishes. In git, a *tag* is a permanent label on the exact code of a release
(e.g. `v1.25.1`); a *release branch* (e.g. `release/v1.25`) collects fixes for
one release line. Taking docs from a tag or release branch guarantees they match
that version.

**Commit SHA** — The unique ID of one exact snapshot in a git repository. Stored
in the manifest so anyone can see precisely which text was copied.

**Stable / pre-release** — A stable release is meant for production. Pre-releases
(`-rc` release candidate, `-beta`, `-dev`) are test builds; the ingest skill skips
them unless asked.

**Semantic versioning (semver)** — The `MAJOR.MINOR.PATCH` numbering scheme
(e.g. `1.25.1`). Major changes may break things, minor adds features, patch fixes
bugs. Many docs sites publish one copy per minor version.

**Markdown** — A plain-text format with light markup (`#` for headings, backticks
for code). Preferred here because it is small, readable and easy to search.

**`llms.txt` / `llms-full.txt`** — A convention where a docs site publishes its
content as plain text for AI tools: `llms.txt` is usually an index of links,
`llms-full.txt` the full text. A good source when it exists and matches the version.

**Per-page Markdown (`<page>.md`)** — Some docs sites publish a Markdown copy of
every page next to the web page (`https://docs.docker.com/engine/install/ubuntu.md`).
The site renders it with its own build, so shared snippets, tabs and generated
reference pages arrive already assembled. `tools/fetch_md_pages.py` fetches every
page listed in the site's sitemap this way. Used for the Docker docs set.

**Snapshot (of an unversioned site)** — Some docs sites, like docs.docker.com,
always show the current release and keep no older versions. A docs set taken from
one is a snapshot of a date, filed under the version the docs describe that day
(`docker/29.9`) and labelled as a snapshot in its manifest's `gaps`.

**Crawl** — Automatically visiting a website's pages by following links, saving
each one. `tools/crawl.py` does this politely (with a delay, obeying `robots.txt`)
and converts each page from HTML to Markdown.

**HTML** — The markup language web pages are written in. Crawled pages are
converted from it to Markdown, dropping menus, headers and footers.

**`robots.txt`** — A file a website publishes saying which pages automated
tools may visit. The crawler obeys it.

**Sitemap (`sitemap.xml`)** — A file a website publishes listing its pages. The
crawler can start from it to find pages that aren't well linked.

**CSS selector** — A pattern naming part of a web page (e.g. `main article`).
`crawl.py --selector` uses one to say which part of each page is the actual
documentation.

**Docs-site generators (Docusaurus, MkDocs, Hugo, VitePress, Sphinx, Mintlify)** —
Tools that build a documentation website from Markdown (or reStructuredText)
files in a git repo. If a site was built with one, its Markdown source usually
exists, and that is the best thing to ingest.

**reStructuredText (`.rst`) / AsciiDoc (`.adoc`) / MDX (`.mdx`)** — Other plain-text
docs formats; MDX is Markdown with embedded components. Kept as-is — they are
still searchable text.

## APIs

**API (application programming interface)** — The defined way programs talk to
a product, e.g. a set of web addresses ("endpoints") accepting requests.

**REST API** — A common style of web API where each resource has a URL and
standard HTTP methods (`GET` read, `POST` create, `PUT`/`PATCH` update,
`DELETE` remove).

**Endpoint / operation** — One URL + method in an API, e.g.
`GET /repos/{owner}/{repo}`. `operationId` is the name a spec gives it.

**OpenAPI / Swagger** — A standard machine-readable file (JSON or YAML)
describing every endpoint, parameter and data shape of a REST API. Swagger 2.0
is the older version, OpenAPI 3 the newer. Stored unchanged in `api/`;
`tools/openapi2md.py` turns it into searchable pages.

**Schema / model** — The described shape of a piece of data (which fields, what
types). Listed in `api/schemas.md`.

**Tag (API)** — A group label in an OpenAPI spec (e.g. "repository", "user").
Not the same as a git tag. `openapi2md.py` writes one file per API tag.

**GraphQL schema (SDL — Schema Definition Language)** — The equivalent of an
OpenAPI spec for GraphQL APIs, which use a single endpoint and a query language.

## Packages and tooling

**Package registry** — A public catalogue of installable packages: npm
(JavaScript), PyPI (Python), crates.io (Rust), the Go module proxy (Go). Used to
list a package's released versions.

**Lockfile / manifest file (of a project)** — Files like `package.json`,
`package-lock.json`, `go.mod`, `pyproject.toml` that record which package
versions a project uses. Read to pick the matching docs version. (Not to be
confused with a docs set's `manifest.json`.)

**Virtualenv (`.venv/`)** — A private Python installation for this folder, holding
the HTML-to-Markdown and YAML libraries the tools need without touching the
system Python. Created by `tools/setup.sh`.

**`rg` (ripgrep)** — A fast command-line text search tool. The main way agents
search docs sets.

**Shallow / sparse clone** — Ways of downloading only part of a git repository:
shallow skips history, sparse skips folders you didn't ask for. `git_docs.sh`
uses both so fetching docs is fast.

**`gh`** — GitHub's command-line tool, used to list a project's releases and tags.

## Semantic search (proposed engine)

**Semantic search** — Finding text by meaning rather than exact words, so
"stop people signing up" finds `DISABLE_REGISTRATION`. The proposed local-docs
search engine combines it with keyword search (see *hybrid search*).

**Embedding / vector** — A list of numbers a model produces for a piece of text,
placed so that texts with similar meaning get similar numbers. Searching means
embedding the question and finding the stored chunks whose vectors are closest.

**Embedding model** — The model that turns text into embeddings. Run locally
through Ollama. Examples: `qwen3-embedding`, `embeddinggemma`, `nomic-embed-text`.

**Dimensions** — How many numbers an embedding has (e.g. 768, 1024). More can
capture more nuance but cost more storage and memory.

**MRL (Matryoshka Representation Learning)** — A training method that lets you
keep only the first N numbers of an embedding and still get useful results,
trading a little quality for less storage. `qwen3-embedding` and
`embeddinggemma` support it.

**Instruction / task prefix** — Text some embedding models expect in front of a
query or document (e.g. "Instruct: … Query: …"). Leaving it off quietly lowers
quality, so the indexer and the search must add it the same way each time.

**MTEB (Massive Text Embedding Benchmark)** — A public leaderboard that scores
embedding models on many tasks. Useful as a first filter, but its scores come
from separate tracks (English, multilingual, code) that can't be compared
directly, and they aren't a test on our own docs.

**Ollama** — A program that runs AI models locally and serves them over a local
web API (`http://127.0.0.1:11434`). Provides the embedding model here.

**Milvus** — An open-source database built for storing and searching vectors,
which also does keyword (BM25) search. Docs: `libraries/milvus/3.0/`.

**Milvus Lite** — Milvus as a Python library that runs inside your own program
and stores data in a local folder. No Docker. Version 3.2.2 pairs with Milvus 3.0.
Only one process may open its data folder at a time, but it can run as a small
server (`milvus-lite server`) that many programs connect to.

**Milvus Standalone** — The full Milvus server on one machine, run in Docker.
More features than Lite, but needs more RAM (8 GB minimum per its docs).

**Collection** — Milvus's word for a table: a set of records sharing one
structure (*schema*).

**Partition key** — A field Milvus uses to group records internally (here, the
library slug) so a search limited to one library only looks at that library.

**Chunk** — A small piece of a document (a section under one heading, an
endpoint, a block of a long page) that is embedded and indexed on its own.
Search results point at chunks, with file path and line numbers.

**Heading path** — The chain of headings a chunk sits under, e.g.
"Gitea 28 › Administration › Config Cheat Sheet › service". Added to each chunk
so a section like "Options" still says what it is about.

**BM25** — The standard keyword-ranking formula. It scores a document higher
when it contains the query's words, especially rare ones. Excellent for exact
identifiers (config keys, function names) where meaning-based search is weak.

**IDF (inverse document frequency)** — The part of BM25 that rates rare words as
more telling than common ones. In Milvus Lite it is counted per storage segment,
not across the whole collection, so scores can be slightly off.

**Sparse vector / dense vector** — Two ways of representing text. Dense: an
embedding (every number used). Sparse: mostly zeros, one slot per word (how
Milvus stores BM25). The engine stores both for every chunk.

**Analyzer** — Milvus's rules for splitting text into words for BM25: a
*tokenizer* (where words break) plus *filters* (lowercasing, stemming, stop
words).

**Hybrid search** — Running a keyword (BM25) search and a meaning (embedding)
search together and merging the two result lists. Catches both "exact config
key" and "how do I…" questions.

**RRF (Reciprocal Rank Fusion)** — A simple, robust way to merge ranked lists:
each result scores by its position in each list, so items ranked well by both
searches rise to the top. Milvus: `RRFRanker`.

**Weighted RRF / adaptive fusion** — RRF where one list counts for more: a result
scores `weight / (k + rank)` from each list. Hybrid search here weights the meaning list
1.5× with k=10 for sentence questions, and treats the lists equally (k=60) for
identifier-shaped queries. Why and the measurements: [Hybrid fusion](search/README.md#hybrid-fusion).

**Identifier-shaped query** — A search of at most three words that contains `_`, `.`,
camelCase or ALL_CAPS, i.e. a name from code or config such as `norm_score` or
`REQUIRE_SIGNIN_VIEW`. Meaning search handles these poorly, so keyword search gets an
equal say, and a hit containing the name word for word is labelled strong.

**Reranker** — An optional second model that re-reads the top results next to
the query and reorders them. More accurate, slower. Ollama has no rerank
endpoint, so it would be added only if testing shows it's needed.

**Similarity / confidence label** — How close a hit is in meaning to the query
(cosine similarity of their embeddings, -1 to 1). Search labels each hit
**strong** (≥ `sure_sim`), **weak** (< `weak_sim`) or **related**, and a weak top
hit gets a "No confident match" notice. The thresholds are calibrated per model on
the question set plus off-topic questions, and are set in `search/settings.json`.

**Near-duplicate collapse** — Showing hits whose embeddings are almost identical
(≥ `dup_sim`, 0.97) once, with the other files listed as "same text also in". Next.js
has many pages copied between its App Router and Pages Router docs.

**Intro chunk** — The part of a page before its first heading; its heading path is
just the docs set and page title. `intro_weight` can lower its hybrid score.

**Provenance** — Where a docs file came from: the upstream ref and commit
(`v16.4.5 @4e5335a`) from the source in `manifest.json` whose `dest` folder holds
the file. Search results show it so answers can cite exactly which docs they used.

**Recall@k / MRR (mean reciprocal rank)** — Scores for a search test set. Recall@5
is "how often the right file is in the top 5". MRR rewards having it at rank 1
over rank 5. Used to pick the embedding model on our own docs.

**MCP (Model Context Protocol)** — The standard way to give Claude Code extra
tools. The engine would expose `docs_search` and similar tools through an MCP
server.

**Collection per model** — Each embedding model (and dimension setting) gets its
own Milvus collection, e.g. `docs_qwen3_embedding_0_6b`, because vectors from
different models can't be mixed. Lets models be compared side by side.

**Question set / eval** — `search/eval/questions.yaml`: 60 realistic questions,
each with the file(s) that answer it, checked by hand. `python -m search eval`
runs them and reports recall@k and MRR; `search/eval/bakeoff.sh` does that for
every candidate model.

**Bake-off (model comparison)** — Indexing the same docs with several embedding
models and scoring each on the question set, to pick the default by measurement
rather than by public leaderboards. Script: `search/eval/bakeoff.sh`; results in
the [Model choice](search/README.md#model-choice) section.

**Version prefix matching** — Searching with version `16` or `16.4` also finds a
docs set filed under an exact release such as `16.4.5`, so callers needn't know
how precisely a folder was named. In `scope_filter` in
[store.py](search/store.py).

**Scoped search** — A search limited to one library (and optionally version),
using the partition key. Agents should scope when they know the library.

**Milvus Lite server** — Milvus Lite running as its own background process
(`python -m search up`), which the indexer and every MCP server connect to,
since only one process may open the data folder. Listens on
`127.0.0.1:19541`.

**gRPC** — The network protocol pymilvus uses to talk to Milvus. It prints
harmless "too_many_pings" warnings against Milvus Lite; the tools silence them
with `GRPC_VERBOSITY=NONE`.

**stdio (standard input/output)** — How Claude Code talks to a local MCP server:
it starts the program (`tools/docs-mcp.sh`) and exchanges messages over its
input and output streams. No network port involved.

**Tokens / throughput** — A token is a word-piece, the unit models read (~4
characters of English). Throughput here is chunks (or tokens) embedded per
second; on this machine's GPU it decides how long indexing takes.

**Doc type** — Whether a page is a *guide*, *API reference* or *release notes*,
worked out from its folder (`api/` or `api-reference/` = API reference). Searches
can be limited to one type.

**API weight** — A number (0.6, in `search/settings.json`) that API reference
results are multiplied by, so their many short pages don't crowd out guides for
ordinary questions. Not applied when the question itself looks like an API
question or a doc type is chosen.

**Search page** — The browser interface to the same search
(`python -m search web`, http://127.0.0.1:7710). For people; agents use the MCP
tools instead.

**Formatted view** — The search page's way of showing a Markdown file as a
rendered page (headings, tables, code boxes) rather than raw text, with the
matching section highlighted. "Source" switches back to raw text with line numbers.

**Sanitize (DOMPurify)** — Cleaning HTML before showing it, removing anything
that could run code (scripts, `onclick` handlers, `javascript:` links). The
formatted view sanitizes every page with the DOMPurify library because docs are
downloaded from the internet. marked is the library that turns Markdown into HTML.

**Vendored library** — A copy of someone else's code kept inside this project
(`search/static/`) instead of downloaded at run time, so the page works offline
and can't change under us. Recorded with its version and licence.

**Licence (of a docs set)** — The terms under which a project's documentation
may be copied. Recorded in each manifest; local-docs only mirrors docs whose
licence allows redistribution. This project's own code is MIT (see `LICENSE`).

**Content Security Policy (CSP)** — A rule the search page sends to the browser
listing what the page may load. Here: only its own scripts, no remote images or
other sites, so even a malicious doc page couldn't call out.

**Callout / admonition** — A highlighted note box in docs ("Tip", "Warning"),
written as `:::tip … :::` in Docusaurus-built docs such as Gitea's.

**127.0.0.1 / localhost** — The address that means "this computer". A server
listening only there can't be reached from other machines on the network. Both
the Milvus Lite server and the search page listen only there.

**Host header / DNS rebinding** — Every web request names the site it's meant for
(the Host header). DNS rebinding is a trick where a malicious web page makes
your browser send requests to a server on your own machine under the attacker's
host name. The search page refuses any request not addressed to `127.0.0.1` or
`localhost`, which blocks it.

**AST (abstract syntax tree)** — A program's code parsed into its structure
(functions, classes). Code-search tools use it to split code at function boundaries;
docs don't need it, because headings already mark the sections.
